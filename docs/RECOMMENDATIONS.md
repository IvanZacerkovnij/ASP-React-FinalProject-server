# Рекомендації постів і користувачів

Реалізація використовує PostgreSQL, наявні таблиці та параметризовані SQL-запити через EF Core. Ранжування, агрегація, фільтрування й обмеження результатів виконуються в БД. Application service формує чинні DTO та керує cursor pagination; контролер лише приймає HTTP-запит. Нових пакетів або зовнішніх сервісів немає.

## API

Обидва endpoints вимагають JWT активного, невидаленого користувача:

```http
GET /api/recommendations/posts?limit=20
Authorization: Bearer <access-token>

GET /api/recommendations/users?limit=20
Authorization: Bearer <access-token>
```

Відповіді: `CursorPageResponse<PostResponse>` та `CursorPageResponse<UserShortResponse>` з `items`, `hasMore`, `nextCursor`. `limit`: 1–50, за замовчуванням 20. Наступна сторінка:

```http
GET /api/recommendations/posts?limit=20&cursor=<nextCursor>
Authorization: Bearer <access-token>
```

Пошкоджений, прострочений курсор або курсор іншого користувача/endpoint повертає `400 application/problem+json`; відсутня чи недійсна автентифікація — `401`.

### Випадкова стрічка рекомендацій

`GET /api/posts/feed` повертає масив до 10 `PostResponse`, як і раніше, та доступний без авторизації. З JWT використовуються персональні сигнали й виключаються власні пости. Для гостя використовуються популярність і свіжість, без персональних сигналів.

Після розрахунку score й різноманітності у PostgreSQL відбирається пул до `ResultLimit` рекомендованих постів. Кожен отримує випадковий пріоритет `-ln(max(random(), 1e-12)) / (1 + score)`: більший score збільшує шанс раннього вибору. Далі `ROW_NUMBER() PARTITION BY AuthorId` забезпечує чергування авторів за цими пріоритетами. Повертаються перші 10 постів; весь відбір виконується в БД. Випадковість застосовується до обмеженого пулу рекомендацій, а не до всіх постів.

Кожен запит формує нову випадкову вибірку. Дублікатів у межах відповіді немає; між незалежними запитами повторення допустимі. Feed не має курсора. Для стабільної пагінації використовуйте `/api/recommendations/posts`. Якщо доступних постів у часовому вікні немає, feed повертає порожній масив. DTO цитат завантажуються пакетно тим самим сервісом, що й у сторінкових рекомендаціях.

## Граф і доступ

Вузли — `Users` і `Posts`. `Follows` — спрямовані user → user ребра. `PostLikes`, `PostReposts`, `PostBookmarks`, `PostViews` і авторство `Comments` — user → post ребра. Реакції з `CommentLikes`, `CommentReposts`, `CommentBookmarks`, `CommentViews` також проєктуються на батьківський пост; це сигнал інтересу до поста та його автора, а не до автора коментаря. Опитування й цитати не додають сигналів ранжування.

SQL явно відтворює чинні EF query filters: `DeletedAt IS NULL`, `User.IsActive`, доступний автор поста; для коментарів — також доступний автор коментаря й батьківський пост. Неактивні та видалені учасники не впливають на граф чи популярність. Після ранжування читання DTO використовує звичайні EF query filters. `IgnoreQueryFilters` не використовується.

У поточній моделі немає приватності постів/акаунтів або таблиці блокувань між користувачами. Адміністративне блокування реалізоване через `IsActive=false`. Налаштування `VisibilityLevel` стосуються лише дати народження; рекомендації використовують публічний `UserShortResponse`, без дати народження чи email. Scheduled posts не входять у `Posts` до публікації. Пости з майбутнім `CreatedAt` не є кандидатами.

Власні пости, сам користувач, недоступні об'єкти та вже наявні підписки виключаються. Повторно рекомендовані пости з попередніх незалежних сесій, переглянуті та лайкнуті пости допустимі; виключення переглянутого контенту не запроваджено.

## Сигнали

Початкові ваги — **евристичні**, а не доведено оптимальні. Їх слід перевіряти на реальних даних і метриках якості.

| Сигнал | Параметр | Вага |
|---|---|---:|
| Лайк поста або коментаря | `LikeWeight` | 3 |
| Коментар до поста | `CommentWeight` | 4 |
| Репост поста або коментаря | `RepostWeight` | 5 |
| Закладка поста або коментаря | `BookmarkWeight` | 5 |
| Перегляд поста або коментаря | `ViewWeight` | 0.25 |

У межах кожного джерела враховується максимум один сигнал на пару `(user, post)`: 50 коментарів не сильніші за один коментар, реакції на кілька коментарів одного поста також не множать сигнал джерела. Декілька різних джерел можна комбінувати. Загальна вага ребра `E(u,p) = min(SignalCap, sum(weights))`; `SignalCap=10`. Композитні ключі таблиць реакцій також не допускають повторних реакцій на той самий target. При запуску валідація вимагає, щоб перегляд був слабший за кожну явну взаємодію.

Взаємодії беруться за останні `HistoryWindowDays=90` днів і не пізніше моменту першого запиту. Для історії поточного користувача кожне з дев'яти джерел спочатку обмежується `HistoryLimit=500` найновішими діями; об'єднану історію додатково обмежено 500 різними постами. Доступність цих постів перевіряється до побудови ребер. Велика кількість коментарів може витіснити старіші дії з вибірки історії, але не збільшує оцінку без обмежень.

## Ранжування постів

Кандидати — до `CandidateLimit=1000` найновіших доступних чужих постів за `PostWindowDays=30` днів. SQL розглядає ребра лише для цих кандидатів і обмеженої історії поточного користувача. Пости поза цим пулом не можуть бути рекомендовані, навіть якщо мають сильні графові сигнали.

Позначення:

- `A(u,a) = min(AuthorCap, sum(E(u,p)))` для постів автора `a`; `AuthorCap=20`.
- `F(u,a)=1`, якщо користувач підписаний на автора, інакше 0.
- Для кожного іншого користувача `v`: `S(u,v) = min(AuthorCap, sum(min(E(u,p), E(v,p))))` на спільних постах, де обидва мають явну взаємодію. Лише перегляди не утворюють спільність.
- До `PeerLimit=100` користувачів з найбільшим `S` утворюють пул схожих користувачів. При рівності обирається більший UUID.
- `C(u,p) = min(CollaborativeCap, sum(E(v,p) * S(u,v) / AuthorCap))`; `CollaborativeCap=30`.
- `P(p) = min(PopularityCap, sum(E(v,p)))`; `PopularityCap=100`.
- `R(p) = 1 / (1 + ageHours / FreshnessHalfLifeHours)`; `FreshnessHalfLifeHours=48`. Через 48 годин свіжість дорівнює 0.5.

```text
postScore = AuthorWeight * A + FollowWeight * F
          + CollaborativeWeight * C + PopularityWeight * P + FreshnessWeight * R
```

| Параметр | Значення |
|---|---:|
| `AuthorWeight` | 1 |
| `FollowWeight` | 6 |
| `CollaborativeWeight` | 2 |
| `PopularityWeight` | 0.2 |
| `FreshnessWeight` | 4 |

Без історії та підписок `A`, `F`, `C` дорівнюють нулю: резервом є популярність і свіжість. Якщо взаємодій немає взагалі, переважає свіжість. Якщо немає доступних постів у часовому вікні, відповідь порожня.

Різноманітність реалізована SQL `ROW_NUMBER() PARTITION BY AuthorId`: спочатку найкращий пост кожного автора, потім другий пост кожного автора тощо. Між авторами порядок визначають score DESC, CreatedAt DESC, Id DESC. Це навмисно дає різноманітності перевагу над абсолютним score; якщо автор лише один, повертаються його пости. Дублікатів ID немає.

## Ранжування користувачів

- `D(u,a)` — кількість підписок поточного користувача, які підписані на `a`: шляхи u → followed → a.
- `H(u,a)` — кількість акаунтів, на які підписані і поточний користувач, і кандидат: спільні вихідні підписки.
- `A(u,a)` — інтерес до контенту автора за тією самою формулою, що для постів.
- `U(a)` — кількість активних невидалених підписників, обмежена `PopularityCap`.

`D` і `H` обмежені `ConnectionCap=20`.

```text
userScore = SecondDegreeWeight * D + SharedFollowWeight * H
          + AuthorWeight * A + PopularityWeight * U
```

`SecondDegreeWeight=4`, `SharedFollowWeight=2`, `AuthorWeight=1`, `PopularityWeight=0.2`. Резерв без історії — популярні доступні акаунти. При рівному score спочатку новіший акаунт, потім більший UUID. За відсутності кандидатів відповідь порожня.

Пул кандидатів — об'єднання до `CandidateLimit` акаунтів другого рівня, до `CandidateLimit` акаунтів зі спільними підписками, авторів з обмеженої історії/пулу постів і до `CandidateLimit` резервних акаунтів. Тому верхня межа цього пулу — `4 * CandidateLimit + HistoryLimit`; це не повний граф у пам'яті застосунку. Кожен підпул обмежується в SQL. Резервна популярність потребує агрегації доступних `Follows` у БД; індекси не усувають вартості цієї агрегації на великому графі.

## Пагінація й конфігурація

Перший запит ранжує до `ResultLimit=200` різних ID у БД. У застосунок надходять лише ці ID і DTO поточної сторінки, а не граф. Порядок фіксується в курсорі разом із user ID, типом рекомендацій та терміном дії. Курсор містить лише решту ID, стискається Brotli та захищається ASP.NET Core Data Protection. Максимальний `ResultLimit` — 200, щоб курсор вміщався у звичайний HTTP request line.

Наступні сторінки не перераховують score: нові взаємодії, пости та зміни ваг не змінюють поточну сесію. Доступність решти ID перевіряється в БД на кожній сторінці; видалені/заблоковані об'єкти й нові підписки вилучаються. Одна послідовність курсорів не повертає вже видані ID. Повторне використання того самого курсора повторює відповідну сторінку. Через конкурентні зміни між перевіркою доступу та читанням DTO сторінка може містити менше `limit` об'єктів; читання DTO також використовує query filters. Цитовані пости й коментарі завантажуються пакетно без N+1, недоступний target має `null`.

`CursorLifetimeMinutes=30`. Після завершення або спливу курсора потрібно почати новий запит без курсора. Нова сесія може повторити раніше показані об'єкти. Це snapshot порядку ID, а не історична копія контенту чи транзакційний snapshot всієї БД.

Всі параметри з таблиць і межі доступні через секцію `Recommendations`. Наприклад:

```json
{
  "Recommendations": {
    "CandidateLimit": 1000,
    "ResultLimit": 200,
    "HistoryLimit": 500,
    "PeerLimit": 100,
    "PostWindowDays": 30,
    "HistoryWindowDays": 90,
    "CursorLifetimeMinutes": 30,
    "LikeWeight": 3,
    "CommentWeight": 4,
    "RepostWeight": 5,
    "BookmarkWeight": 5,
    "ViewWeight": 0.25,
    "FollowWeight": 6,
    "AuthorWeight": 1,
    "CollaborativeWeight": 2,
    "FreshnessWeight": 4,
    "PopularityWeight": 0.2,
    "SecondDegreeWeight": 4,
    "SharedFollowWeight": 2,
    "SignalCap": 10,
    "AuthorCap": 20,
    "CollaborativeCap": 30,
    "PopularityCap": 100,
    "ConnectionCap": 20,
    "FreshnessHalfLifeHours": 48
  }
}
```

Також працюють environment variables, наприклад `Recommendations__LikeWeight=3`. Невалідні значення відхиляються під час запуску. `ResultLimit` не може перевищувати `CandidateLimit`. Зміни конфігурації набувають чинності після перезапуску.

Для декількох API-інстансів потрібно спільне стале сховище ключів Data Protection; інакше курсор з іншого інстанса може повертати 400. Без збереження ключів перезапуск контейнера також може зробити попередні курсори недійсними.

## Індекси та перевірки

Перевірені наявні індекси: унікальний `(FollowerId, FollowingId)`, індекси `Follows` з обох кінців, композитні ключі `(PostId, UserId)`/`(CommentId, UserId)` та індекси за користувачем у реакціях, `Comments.AuthorId`, `Comments(PostId, CreatedAt, Id)`, `Posts(AuthorId, CreatedAt, Id)`.

Міграція `AddRecommendationPostIndex` додає лише частковий індекс `Posts(CreatedAt, Id) WHERE DeletedAt IS NULL` для глобального відбору свіжих кандидатів; авторський індекс не покриває таке сортування. Model snapshot і target model міграції оновлені. Міграція не застосовувалась до зовнішньої БД; integration tests застосовують її до власного PostgreSQL-контейнера.

Перевірки покривають PostgreSQL SQL, сигнали авторів/схожих користувачів, свіжість, зміну ваг, caps повторних коментарів, різноманітність, fallback, виключення недоступних об'єктів і нових підписок, детерміновані ties, ліміти, cursor scope/expiry/tampering, DTO цитат та HTTP `ProblemDetails`. Для виробничих обсягів потрібні додаткові вимірювання `EXPLAIN (ANALYZE, BUFFERS)` і навантажувальні тести: функціональні тести не доводять масштабованість чи оптимальність ваг.
